# Инструкции для ИИ-агента, работающего в этом проекте

Это готовый рабочий пайплайн, а не заготовка. Две типичные задачи, с которыми сюда
приходят:

1. **Запустить сбор по региону и довести его до конца** (кейс площадок Казахстана).
2. **Перенастроить проект на другую тему** — тогда правь `collect.queries` и
   `collect.rubrics` в `config.yaml`, а не код. Списки в `rubrics.py` и `queries.py` —
   встроенные наборы под исходный кейс, конфиг их полностью заменяет.

Подробный сценарий запуска для первой задачи: [PROMPT-AGENT.md](PROMPT-AGENT.md).

## Порядок при запуске сбора

```bash
pip install -r requirements.txt   # playwright install НЕ нужен: берём системный Chrome
python run.py doctor              # проверка машины и рекомендация по числу окон
python run.py regions             # коды регионов и что уже собрано
python run.py collect --region <код> --workers <из doctor>
python run.py export              # выгрузка в out/
python run.py pack --author "имя" # архив для отправки координатору
```

Долгие команды запускай в фоне и следи за `logs/` — у каждого воркера свой файл.

## Что нельзя делать

- **Не выдумывать данные.** Если 2GIS не отдал вместимость или телефон — поле остаётся
  пустым. Это осознанное правило проекта, а не недоработка.
- **Не запускать `playwright install`.** Проект подключается к системному Chrome по CDP;
  сборка Chromium от Playwright палится антиботом.
- **Не ставить `--headless` по умолчанию.** Заметно повышает риск защитной страницы.
- **Не поднимать больше воркеров, чем сказал `doctor`.** Выше числа физических ядер
  скорость не растёт, а доля неудачных карточек утраивается.
- **Не запускать два прогона в одной папке одновременно** — они дерутся за профили Chrome.

## Устройство

Сбор идёт в две фазы через общую очередь в SQLite (`data/state.sqlite`):

- **Фаза A** (`discover.py`) — листает выдачу рубрики или поискового слова и складывает
  найденные `firm_id` в очередь. Карточки не открывает.
- **Фаза B** (`cards.py`) — открывает каждое заведение ровно один раз за прогон
  и вытаскивает поля из перехваченного ответа `items/byid`.

Воркеры (`worker.py`) — отдельные процессы, каждый со своим профилем Chrome. Сначала
разбирают фазу A, когда она кончилась — переходят на фазу B. Оркестратор
(`orchestrator.py`) только планирует очередь и поднимает процессы.

Выгрузка (`export.py`) строится целиком из сырых JSONL и браузер не трогает — пересобирать
её можно сколько угодно раз, меняя правила нормализации задним числом.

## Грабли, на которые уже наступали

- **Селектор `a[href="<точный href>"]` использовать нельзя.** После открытия первой
  карточки в DOM остаётся второй, неактивный список с теми же href, и клик уходит
  в пустоту: задача крутится вхолостую и помечается выполненной. Правильно —
  `a[href*="/firm/<id>"]` плюс клик по видимому элементу.
- **Переход на `/page/N` через URL сбрасывает выдачу на первую страницу.** Страницы
  переключаются только кликом по ссылке в DOM.
- **Chrome — single-instance на профиль.** Если с прошлого прогона остался живой процесс,
  новый запуск молча отдаст ему URL и завершится, а CDP-порт не откроется. Поэтому
  перед стартом процессы, держащие профиль, убиваются (`kill_browsers_using_profile`).
- **У каждого воркера должен быть свой профиль** — иначе они расстреливают браузеры
  друг друга при каждом перезапуске.
- **Флаги запуска доходят до воркеров только через `data/.effective-config.yaml`**,
  который пишет оркестратор. Воркеры — отдельные процессы и читают конфиг с диска.

## Если правишь код

Комментарии и сообщения — на русском, как во всём проекте. Объясняй в них **почему**,
а не что делает строка. Перед изменением логики сбора проверь дымовым прогоном:

```bash
python run.py collect --region taraz --workers 1 --max-pages 1 --max-seconds 100
```
